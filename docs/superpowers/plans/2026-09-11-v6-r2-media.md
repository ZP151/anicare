# v6 R2 media, feed and navigation implementation plan

> For agentic workers: use superpowers:subagent-driven-development task by task. The user approved the design and active 0.4.0 delivery goal; routine implementation choices do not require another approval.

**Goal:** Publish and recover real 1–6-image community posts, browse them from the compact Home grid and open real activity notifications through the new four-tab plus creation-action navigation.

**Architecture:** Preserve all legacy community RPC responses. Add independent media jobs, ordered attachments, batch post extras and owner-scoped activity. Reuse the existing local JPEG processor, cryptography, public visibility and community mutations. Stored uploads remain private until one database publication transaction attaches a complete validated set; object cleanup is a separate idempotent operation.

**Tech Stack:** Existing Expo/RN, encrypted SQLite/SecureStore, Supabase SQL/Storage/Edge. No dependency upgrade planned.

**Spec:** `docs/plans/2026-09-11-social-v6-iteration.md`, approved 2026-09-11. R1 implementation precedes this plan in the same isolated worktree.

## Global constraints and rulings

- Preserve 0.3.1's exact nine-field CommunityPost response and six-field reply response. New columns never silently enter old RPC projection.
- Images: JPEG only; maximum six attachments, ordered first-cover. Display <=2048px /4MiB, thumbnail <=480px /512KiB. Each variant goes through actual JPEG inspection, not a filename/MIME check. Existing `inspectJpeg` parses image structure and rejects metadata.
- No fabricated sightings for uploads, no public bucket, no personal report images reused. Publish is distinct from cat identity/location claims.
- Existing signer/CI deployment and lock-file checks remain; no ordinary-post manual audit gate is added.
- Ruling: R2 uses a genuine interaction inbox; private conversations and nested comments remain R3. This avoids a dead Messages page while preserving the approved sequencing.
- Ruling: preserve native material through existing GlassSurface if a custom four-tab bar is required for the centre action. Installed NativeTabs emits non-cancellable tabPress; its disabled-tab callback is not a reliable accessible action button. Do not navigate to a dummy page and then redirect.

## Task A — Media storage and atomic publication

Create `supabase/migrations/202609110015_community_media.sql`, `supabase/tests/037_community_media.sql`, `supabase/functions/community-media/{index.ts,deno.json}`, `supabase/functions/cleanup-community-media/{index.ts,deno.json}` and testable `_shared/community-media-*` modules/tests. Extend erasure cleanup caller in Admin after reading its AGENTS.md. Update exact source/deployment inventories once the final file list is known.

Service-only interfaces:

```ts
type Variant = { sha256: string; byteLength: number; width: number; height: number };
type Reservation = { jobId: string; reservationExpiresAt: string;
  uploads: { thumb: { signedUrl: string; token: string }; display: { signedUrl: string; token: string } } };
// POST community-media: {action:'reserve', requestId, thumb:Variant, display:Variant}
// POST community-media: {action:'finalize', jobId} -> {mediaId:string}
// GET community-media?postId=...&mediaId=...&variant=thumb|display -> JPEG bytes
```

SQL holds job owner, request ID/payload hash, variants, stable private object paths, expiry, validated/attached/deletion state and ordered post attachment relation. New publication RPC `create_community_post_with_media(p_body,p_title,p_cat_id,p_community_slug,p_media_ids,p_request_id)` accepts 0–6 IDs for compatibility with text posts. It validates all owned/unexpired/unattached jobs and the current post subject before calling or reusing the existing post mutation in one transaction. New idempotency record includes title and ordered media IDs; collision with a previously used legacy request ID fails. Exact replay returns the same post, changed order/body/attachments conflicts. Acquire owner/account lock consistently with deletion and lock media jobs in stable order.

Batch reader `get_public_community_post_extras(p_post_ids uuid[])` returns exactly `{postId,title,media:[{mediaId,width,height}]}` per currently visible post, in attachment order; no bucket paths. Legacy post methods and My Posts remain unchanged. Media GET validates optional caller token and resolves the requested attached media against `private.community_post_available` on every fetch, returns no-store bytes, rejects arbitrary paths/variants. Guest images remain readable when the post is public; an invalid supplied identity does not silently become guest. Avoid long-lived signed download URLs that outlive visibility checks.

Reservation/finalization are service-only SQL, bounded to active eligible account with per-owner pending quota and expiry. Reserve replay cannot mint indefinitely extended credentials. Validate expected lengths, hashes and decoded dimensions of BOTH downloaded variants before marking valid. Duplicate finalize is safe. Limit body size and downloaded bytes; CORS follows existing allowlist and bearer auth. No logs containing source media, tokens or storage paths.

Post deletion and owner erasure invalidate reads immediately and enqueue both variants. A hidden post stays unreadable but may retain attachments for restore. Expired unbound jobs are collected. Cleanup cannot run before upload credentials expire (2h15 bound) so a late signed upload cannot resurrect objects; retry/claim token protects concurrent workers. Extend account-erasure cleanup links and completion predicate for community media and invoke the new cleanup worker from the existing erasure processor. Scheduled recurring cleanup remains R4; expose accurate pending state rather than reporting files already deleted.
